## 1. What actually serves h2 — recommendation

**Recommend: `golang.org/x/net/http2.Server.ServeConn` for the client side, and a
per-`Handle` `*http.Transport` with `ForceAttemptHTTP2: true` for the upstream
side.**

Three options were considered.

### A. x/net/http2 `Server.ServeConn` + `http.Transport` (RECOMMENDED)

`ServeConn` is the only API in the ecosystem that takes a `net.Conn` we have
already handshaken and serves h2 on it, blocking until the conn dies. That is
*exactly* the shape `Handle` already has: `Handle` owns the conn, owns the TLS
termination (it must — it holds the per-session CA and the ClientHello hook), and
returns when the conn is finished. Nothing else fits without inversion of control.

- No new dependency **tree**: `x/net` v0.54.0 is already resolved and already
  licensed. The change is a `go.mod` require-block move (indirect → direct).
- Exposes the knobs we need to be explicit about (`MaxConcurrentStreams`,
  `MaxReadFrameSize`, `MaxUploadBufferPerStream/PerConnection`, `IdleTimeout`).
- Same code the stdlib bundles, so behaviour matches what clients already expect.

### B. Rewrite onto `net/http` Server/Transport (no new dep)

Achievable: wrap the single client conn in a one-shot `net.Listener` and call
`srv.ServeTLS(oneShot, "", "")` with `TLSConfig.NextProtos = ["h2","http/1.1"]`;
`net/http` then handshakes and dispatches to its bundled h2 via
`TLSNextProto`. Go 1.26 even exposes `Server.HTTP2` / `http.HTTP2Config` and
`http.Protocols`, so the old "the bundled h2 is unconfigurable" objection is
mostly gone.

**Rejected**, for two concrete reasons:

1. **Control inversion.** `http.Server` wants to own the accept loop and its own
   lifetime (`Shutdown`/`Close`); `Handle` is per-connection and synchronous.
   Bending a Server around one conn means a fake listener, a shutdown channel,
   and reasoning about which of `Serve`'s exits mean "this conn is done" — pure
   accidental complexity next to a call that already means what we want.
2. **We must handshake ourselves.** `GetConfigForClient` is where the ALPN offer
   is visible and the per-session cert is minted from the cert cache. Handing TLS
   to `http.Server` is possible but puts the CA path behind someone else's
   handshake, for zero gain.

The dependency argument for B is also weaker than it looks: it saves nothing,
because x/net is already compiled into the build.

### C. `httputil.ReverseProxy` as the h2 handler

Tempting — it already solves trailers, `TE: trailers` preservation, SSE
flush-detection, hop-by-hop stripping, and client-cancel propagation, all of
which we would otherwise re-derive (and get wrong; see §9). It is **not rejected
outright**: the recommendation is to *steal its logic*, not adopt it wholesale.

Rejected as the primary structure because a `ReverseProxy` h2 path beside a
hand-rolled 1.1 loop is **two transports with two behaviours behind one policy** —
precisely the drift AGENTS.md/ADR 0034 name as a bug class. The `Director`/
`ModifyResponse` seams also fit the policy model badly (deny must synthesize a
response *before* the request leaves; `ModifyResponse` is too late, and the
`RoundTripper` seam we would use instead is available to us anyway without
ReverseProxy).

**Consequence to accept and state in the ADR:** we take on ReverseProxy's
correctness burden by hand. §9 lists the specific behaviours to port and cite.

### Dependency process (AGENTS.md)

- [ ] **ADR required** — "New libraries require an ADR justifying the addition".
      An indirect→direct promotion is arguably not a new library; write it
      anyway, since the ticket asks and the *decision* (why x/net over net/http
      over ReverseProxy) is exactly what an ADR is for. Slug ≤3 words, e.g.
      `00NN-serve-http2-mitm.md`. Number from main at merge time.
- [ ] `make licenses` — expect a no-op diff (x/net is already listed); CI fails
      the release if `THIRD_PARTY_LICENSES` is stale, so run it, don't assume.

## 2. How the tunnel + per-session CA + cert cache survive

**Unchanged, entirely.** Everything before the handshake stays byte-for-byte:

- `internal/tunnel/handler.go` still calls `mh.Handle(c, hostname, "443")`. No
  gateway change.
- `ParseHostTarget` normalisation (AGE-220), `certCache.get/put`, `SignHostCert`
  against the in-memory CA (ADR 0076 S-C1), the IP-SAN behaviour — untouched.
- `GetConfigForClient` stays. Its body changes (§5): it stops being a downgrade
  notice and becomes nothing at all, or is deleted with `alpn.go`.

Two lines change in the client `tls.Config`:

```
NextProtos: []string{"h2", "http/1.1"}      // was: {"http/1.1"}
```

and after `Handshake()` we branch on
`clientTLS.ConnectionState().NegotiatedProtocol`.

**The real change is upstream, and it is not cosmetic.** Today `Handle` dials
**one** upstream TLS conn up front and the 1.1 loop reuses it. That model cannot
survive h2 (§9, trap 1): one client conn now carries N concurrent streams, and if
the upstream turns out to be HTTP/1.1-only, one upstream conn cannot serve them.
So:

> Replace the eager single `tls.Dial` with a per-`Handle` `*http.Transport` that
> owns upstream dialling and pooling, and let *it* negotiate upstream ALPN.

```
tr := &http.Transport{
    TLSClientConfig:   upstreamTLS,          // ServerName=host, MinVersion 1.2, system roots
    ForceAttemptHTTP2: true,                 // required: we set a custom TLSClientConfig
    DialContext: func(ctx, network, _ string) (net.Conn, error) {
        // Pinned: ALWAYS the tunnel target, never the request's authority.
        return dialer.DialContext(ctx, "tcp", target.DialAddr(port))
    },
    MaxIdleConnsPerHost: ...,
}
defer tr.CloseIdleConnections()
```

Properties this buys, which should be stated in the ADR because they are
security-relevant, not just plumbing:

- **`DialContext` ignores the address `Transport` asks for and dials the tunnel
  target.** A stream cannot redirect us by forging `:authority`/`Host`. (See §9
  trap 2 for why that is necessary but not sufficient.)
- **Upstream ALPN is negotiated per upstream conn, and h2↔1.1 bridging is free.**
  `http.Transport` speaks whichever the origin offers; our handler only ever sees
  `*http.Request`/`*http.Response`. This is what makes "client h2, upstream 1.1"
  work instead of regressing.
- `UpstreamTLSConfig` (tests-only override) keeps its meaning — it becomes
  `tr.TLSClientConfig`. `policy_test.go:70`, `policy_test.go:186`,
  `requestsize_test.go:44` set it; they should keep compiling, or change in one
  obvious way.

**Cost to accept:** we lose "exactly one upstream conn per client conn". Upstream
conn count is now `Transport`-managed. Also `tr` must be closed on every `Handle`
exit or we leak idle conns per tunneled connection.

## 3. netpolicy per h2 stream, and what a deny looks like

**The seam does not change, because it was never HTTP/1.1-specific.**
`RecognizeHTTP(host, req *http.Request, bodyBytes []byte)` takes an
`*http.Request`; the h2 server hands the handler an `*http.Request` with
`ProtoMajor: 2`, `Method`, `URL.Path`, `Header` all populated. `Matcher.Evaluate`
takes an `*Operation`. Both are already protocol-agnostic. **This is why the
ticket is a transport change, not a policy change.**

Per stream, in `ServeHTTP`:

1. `op := netpolicy.RecognizeHTTP(host, req, bodyBytes)` — where `bodyBytes` is
   governed by §4's Content-Length rule (possibly nil).
2. `result := h.Matcher.Evaluate(op)`; populate a **per-stream** `RequestLog`.
3. Deny → write it and return. Allow → `tr.RoundTrip(outreq)`.

### Expressing a deny in h2

There are three plausible expressions; pick per content-type, and **say so**:

| Client | Deny expression | Why |
|---|---|---|
| h2 (non-gRPC) | `403` + the existing JSON body + `X-Agentjail-Deny: <template>` | Identical to the 1.1 path. `rw.WriteHeader(403)`, `rw.Write(body)`. The h2 server frames it; no `http.Response{ProtoMajor:1}` literal. |
| gRPC (`Content-Type: application/grpc*`) | `200` + `grpc-status: 7` (PERMISSION_DENIED) + `grpc-message` | A bare 403 surfaces to grpc-go as `INTERNAL: unexpected HTTP status code 403` — technically a denial, but it reads as our bug rather than our policy. |
| never | `RST_STREAM` | A stream reset is indistinguishable from a network fault. A deny must be legible. ADR 0077's spirit: never let policy look like weather. |

The gRPC-shaped deny is its own commit (§7 C7) and its own line in the ADR, not a
silent detail.

**Do not reuse the 1.1 deny code path as-is.** `mitm.go:228` builds an
`http.Response{ProtoMajor:1, ProtoMinor:1}` and calls `denyResp.Write(clientTLS)`.
That writes HTTP/1.1 wire bytes onto a TLS conn. Inside an h2 stream that is
garbage. Factor the *content* (status, headers, JSON body) into a shared
constructor; keep the *writing* per-transport. That shared constructor is the
anti-drift device (§7 C1).

## 4. D1 body capture, per stream, without buffering

This is the part that most needs D1 to land first: the plan builds on D1's sink,
it does not re-invent one.

### Response direction (the load-bearing constraint)

D1: *"Capture tees, and must never buffer a response before forwarding it"* —
the SSE model turn streams ~14s and buffering reproduces the Burp hang.

Per stream:

```
// resp.Body → client, teeing into D1's sink, flushing as we go.
copyAndFlush(rw, io.TeeReader(resp.Body, sink), rw.(http.Flusher))
```

**Trap that will bite:** `io.Copy(rw, io.TeeReader(...))` alone is NOT enough on
h2 and is *worse* than the 1.1 path. `http2`'s `responseWriter` buffers behind a
~4KB `bufio` writer and flushes on handler return or explicit `Flush()`. An SSE
stream emitting 200-byte events would sit in that buffer — we would reproduce the
exact Burp hang D1 exists to avoid, **while passing a naive "we didn't buffer"
review**, because the buffering is in x/net, not in our code. The h2 path
therefore needs an explicit flush-per-write copy loop (this is
`httputil.ReverseProxy`'s `maxLatencyWriter` with `FlushInterval: -1`; port it or
cite it).

**Test the constraint, don't assert it:** D1's invariant list already demands
"test with a real SSE endpoint and assert first-byte latency is unchanged". Add
the h2 variant of that test in the same commit as the h2 tee.

### Request direction

Wrap `req.Body` in a `TeeReader` into the request sink before handing it to
`RoundTrip`, and keep the existing `countingReader` for `RequestSize` (AGE-243's
fix must not regress on the new path — a streaming h2 upload has no
Content-Length, so the counter is the *only* source of truth for its size).

### Policy scanning vs capture — they are different questions on h2

The ticket's central blocker: `io.ReadAll(io.LimitReader(req.Body, maxBodyScan+1))`
on a bidi-streaming RPC blocks until 1 MiB or EOF — a deadlock. **Capture** is
fine (it tees, it never waits). **Policy scan** is the problem, because scanning
requires *having* the bytes before forwarding.

Three candidate rules, and the recommendation:

- **(a) Never body-scan on h2.** Honest and simple; but silently drops
  `scan.payload` coverage for every h2 REST call (Anthropic's `/v1/messages`
  is a plausible h2 endpoint), which is a big, invisible policy hole.
- **(b) Bounded first-frame peek with a timeout** — read up to N bytes or 50ms,
  whichever first. **Reject.** A policy decision that depends on wall-clock is
  bypassable by construction: an attacker slow-writes the body and the scan is
  skipped. A security control must not be defeatable by `sleep`.
- **(c) Content-Length gate (RECOMMENDED).** If the h2 request declares
  `Content-Length`, pre-drain up to `maxBodyScan` exactly as the 1.1 path does
  (bounded, deterministic, no deadlock — the bytes are declared to be coming, and
  a client that declares-then-stalls only stalls its own stream because h2
  multiplexes and each stream has its own goroutine). If it does not, forward
  without body scanning.

Why (c): gRPC **never** sets Content-Length → gRPC gets header/method/path policy
and no deadlock, which is what the ticket asks for. Unary h2 REST usually does →
it keeps full body policy. The rule is deterministic and states its own coverage.

**The Open Question must be answered in the ADR, not left implicit** (ADR 0077
rejects exactly the failure mode of a template that matches on 1.x and silently
never matches on h2):

> Body-level policy (`scan.payload`) applies to an h2 request **iff** the request
> declares a Content-Length. Unknown-length h2 request bodies (all streaming RPCs)
> are policy-evaluated on headers, method and path only. h2 **response** bodies
> are not policy-inspected — same as HTTP/1.x today.

And it must be **surfaced**, reusing AGE-222's own shape (once per session, an
audit event + a log line): when a body-scanning template is loaded *and* an
unknown-length h2 request is forwarded, emit `TunnelBodyScanSkipped` (or similar)
naming the host and template. This is the AGE-222 pattern retired and immediately
re-applied to the next honest limitation — which is the right instinct, and is
cheap because the machinery already exists in `alpn.go`.

**A fail-closed knob (deny unknown-length requests when a body template is
loaded) is deliberately NOT in scope** — that is a posture decision with its own
consequences and belongs to its own ticket. Note it in the ADR's Consequences.

`maxBodyScan` stays 1 MiB and stays the *scan* window. D1 already says so.

## 5. HTTP/1.1 clients, and ALPN dispatch

```
NextProtos: []string{"h2", "http/1.1"}
...
switch clientTLS.ConnectionState().NegotiatedProtocol {
case "h2":
    h.serveH2(clientTLS, host, port, target)   // http2.Server.ServeConn — blocks
default:                                       // "http/1.1" or "" (no ALPN offered)
    h.serveHTTP1(clientTLS, host, port, target) // today's loop, verbatim
}
```

- `""` (client sent no ALPN extension at all — older clients, some Java stacks)
  must fall to 1.1. Do not `switch` on `"http/1.1"` alone and let `""` fall off a
  cliff.
- **What breaks for 1.1 clients: nothing, by construction** — the loop is moved
  into `serveHTTP1` unchanged in the same commit that adds the dispatch, so the
  diff is a move, and `policy_test.go`/`expect_continue_test.go`/
  `requestsize_test.go` are the regression gate.
- ...with **one** exception, and it is a real one: §2 changes the upstream from a
  pre-dialed conn to a `Transport` **for both paths**. If we do that, the 1.1
  path's `req.Write(upstream)` / `http.ReadResponse(upstreamBuf, req)` /
  `Expect: 100-continue` / `req.Close` handling all change. **Do not do that.**
  Recommended: **the 1.1 path keeps its pre-dialed upstream conn and its loop; the
  h2 path gets the Transport.** They diverge in transport and converge at the
  policy/capture seam (§7 C1). Unifying them onto one handler is a follow-up
  ticket, explicitly out of scope here, and named as such in the ADR.
  - Cost: the eager `tls.Dial` currently happens *before* we know the ALPN. Move
    it into `serveHTTP1` so the h2 path never dials an unused upstream conn. That
    is a behaviour change to watch: today an upstream dial failure closes the
    conn before any request is read; after the move, a 1.1 client sees the same
    thing (dial still precedes the read), so no visible change. Verify.
- **New failure mode to note in GOTCHAS:** with `NextProtos` non-empty, a client
  whose ALPN list has **no overlap** with ours gets a `no_application_protocol`
  handshake *failure*, not a downgrade. That is already true today (AGE-222: an
  h2-only client fails the handshake — which is what "gRPC fails" concretely
  means). After this ticket the overlap is wider, so this gets strictly better;
  it does not go away (e.g. an h3-only or exotic-ALPN client).

### Retiring AGE-222

`offersH2`/`noteH2Downgrade`/`h2Noted`/`GetConfigForClient` exist only to report a
downgrade that will no longer happen. Once h2 is served:

- Delete `internal/mitm/alpn.go` + `alpn_test.go`, drop the `h2Noted` field, drop
  `GetConfigForClient`.
- Keep the `audit.TunnelALPNDowngraded` constant? **No** — but do not silently
  delete either: if §4's `TunnelBodyScanSkipped` lands, the *shape* is preserved
  where it is still true. Prefer repurposing the once-per-session helper rather
  than deleting and rewriting it a week later.
- Update `docs/GOTCHAS.md` §12 ("Advertise what you serve"): the trap about
  `NegotiatedProtocol` not showing the client's offer is still true and worth
  keeping; the "we serve http/1.1 only" framing is not.

## 6. gRPC specifics — and does gRPC actually work after this?

**Honest answer: probably, and the plan should be judged on whether it finds out
before shipping rather than on this paragraph.** Four things stand between us and
a working RPC:

1. **`TE: trailers` must survive.** `TE` is a hop-by-hop header, on every
   standard strip-list, and gRPC *requires* it. `httputil.ReverseProxy` carries a
   special case to preserve `TE: trailers` specifically. If we hand-roll header
   copying (we will), we must replicate it. This is the single most likely cause
   of "gRPC still doesn't work" after a plausible-looking implementation.
2. **Trailers, upstream → client.** `http.Response.Trailer` is populated only
   *after* the body reads to EOF. So: copy the body first, **then**
   `for k, v := range resp.Trailer { rw.Header()[http.TrailerPrefix+k] = v }`,
   then return. The `TrailerPrefix` convention is what lets us send trailers that
   were never announced in a `Trailer:` header — which is what gRPC does. Getting
   the ordering wrong (setting them before the copy) silently drops `grpc-status`
   and every RPC reports an opaque error.
3. **Trailers, client → upstream.** `req.Trailer` on the way out. Rarer; still
   copy it.
4. **Trailers-only responses — UNRESOLVED, see §8.** A gRPC error can arrive as a
   single HEADERS frame with END_STREAM and `grpc-status` in it. It is not clear
   from reading alone whether Go's h2 `Transport` surfaces those in
   `resp.Header` or `resp.Trailer`, nor whether re-emitting them as
   HEADERS + empty-DATA(END_STREAM) — which is what our handler naturally
   produces — is accepted by grpc-go as Trailers-Only. **This is the spike.**

Also: gRPC never sets Content-Length → §4(c) means gRPC gets header-only policy,
which is stated, not silent. `grpc-timeout` and deadline propagation ride as
headers and need nothing from us; client cancellation propagates via
`req.Context()` if the outbound request carries it (`outreq := req.Clone(req.Context())`).

## 8. What I could not determine — spike these

1. **Trailers-only gRPC responses (blocks C6/C7).** Does Go's h2 `Transport`
   surface a HEADERS+END_STREAM response's `grpc-status` in `resp.Header` or
   `resp.Trailer`? And does grpc-go accept our re-emission (HEADERS, then an empty
   DATA with END_STREAM) as Trailers-Only, or does it require the single-frame
   form we cannot produce through the `http.Handler` abstraction? **Spike:
   30 lines — a grpc-go server returning `status.Error` immediately, proxied
   through a `ServeConn`+`Transport` pair, assert the client's status.** If the
   answer is "cannot produce", C7's design changes and the ADR must state that
   gRPC *errors from the origin* degrade to a generic error through the proxy —
   which would be a significant caveat, not a footnote.
2. **`ForceAttemptHTTP2` with a custom `DialContext` + custom `TLSClientConfig`.**
   Reading the docs says it works (the flag exists precisely to re-enable h2 when
   a custom TLS config would otherwise disable it), but *reading is not knowing*.
   **Spike: assert `resp.ProtoMajor == 2` against an h2 `httptest.Server` through
   exactly the Transport from §2.** If it does not, the fallback is
   `http2.ConfigureTransports(t1)` (verified present at
   `transport_common.go:34`).
3. **Does anything in the wild actually offer h2 to us today?** AGE-222's audit
   event (`TunnelALPNDowngraded`) is *already deployed*. **The cheapest possible
   spike is to read the audit log** and find out who is offering h2 and to which
   host before building any of this. If the answer is "nothing but curl", the
   priority (Medium) is right and the ADR's Context has real numbers in it —
   which is the standard ADR 0092 set for this repo (it measured real sessions).
   If the answer is "nothing at all", that is worth knowing before spending 3 days.
4. **Test-only gRPC dependency.** C10 wants `google.golang.org/grpc` — a large
   tree, even in `_test.go`. It is not in `go.mod`. Is a test-only dep exempt from
   the ADR rule and from `THIRD_PARTY_LICENSES`? Unclear; assume **not exempt**
   and get a ruling before C10. Fallback: hand-roll the gRPC framing in the test
   (it is 5 bytes of prefix + protobuf) and assert on trailers directly — ugly,
   dependency-free, and arguably tests *our* layer more precisely anyway.
5. **macOS.** ADR 0077: "macOS runs transparent-only regardless" (AGE-149 open).
   So this ships Linux-only in practice. Per ADR 0034 the *contract* (serve what
   you advertise) is shared and `internal/mitm` is OS-agnostic Go — so there is no
   per-OS split to write here. Worth one line in the ADR so nobody looks for one.

## 9. Adversarial: what is most likely to go wrong

Ordered by (likelihood × how quietly it fails).

1. **The SSE/streaming hang comes back, in x/net rather than in our code.**
   §4. `io.Copy` into an h2 `ResponseWriter` buffers ~4KB. A reviewer greps for
   `ReadAll` and `bytes.Buffer`, finds none, and approves — and interactive token
   streaming dies for every h2 client. This is D1's central constraint being
   violated by *omission of a `Flush()`*. **The only defence is the SSE test in
   the same commit (C5).** This is my top concern.
2. **`:authority` ≠ the tunnel target — a new attack surface h2 creates.**
   On 1.1, one conn = one target, and a forged `Host` header was at worst a lie in
   the log. On h2, every stream carries its own `:authority`, and a malicious
   in-sandbox agent can open one TLS conn to `allowed.com` (getting a cert for
   `allowed.com`) and send streams with `:authority: evil.com`. Our pinned
   `DialContext` means the bytes still go to `allowed.com` — safe — but
   `RecognizeHTTP(host, ...)` is called with the *cert* host while the request
   claims another, so **the log and the policy verdict disagree with the request**.
   Some origins route on `:authority`. **Mitigation: reject any stream whose
   `:authority` (`req.Host`) does not match the tunnel target with a 421 or 400,
   and audit it.** This belongs in C4 and in the ADR; it is not optional and it is
   the kind of thing that gets discovered by a researcher rather than by us.
   (Connection coalescing proper is not a risk — our leaf cert covers one host —
   but a hostile client does not need coalescing to *try*.)
3. **`TE: trailers` gets stripped and gRPC "still doesn't work".** §6.1. The
   symptom is generic and the cause is one line in a strip-list. Budget debugging
   time or port ReverseProxy's special case verbatim with a citation.
4. **A slow D1 capture sink stalls a whole connection, not one request.** New with
   h2: streams share connection-level flow control, so if the tee into
   `network.db` blocks on disk, backpressure propagates to the conn and **every
   other stream on it stalls**. On 1.1 a slow sink slowed one conn. D1's sink must
   be non-blocking or bounded-with-drop; if it is not, h2 turns a latency bug into
   a stall. **Raise this with whoever is implementing D1 now**, before C5 — it may
   change D1's sink design, and finding out after both land is expensive.
5. **The two transports drift.** The whole point of C1. A fix applied to the 1.1
   loop and not the h2 handler is the `shield_linux.go`/`shield_darwin.go` story
   again, on a new axis. Named exceptions only; and the follow-up ticket to unify
   both onto one handler should be filed *when this merges*, not "eventually".
6. **The Content-Length gate (§4c) surprises someone.** A `scan.payload` template
   that fires on a 1.1 client and not on the same request over h2 is ADR 0077's
   nightmare, and the gate makes it *real but stated*. The once-per-session notice
   is what keeps it honest — if that notice gets cut for scope, the gate becomes
   the silent policy no-op ADR 0077 rejects. **The notice is not optional; it is
   the price of the gate.**
7. **`Transport` leak.** One `*http.Transport` per `Handle`, one `Handle` per
   connection, an agent opening hundreds of conns. `defer tr.CloseIdleConnections()`
   on every exit path, and a test that counts goroutines/conns after N tunneled
   connections. Easy to write, easy to forget, fails as slow resource growth in
   production and never in CI.
8. **ADR/plan number collisions** (see the header). Cheap to avoid, tedious to fix.

## 10. Definition of done

- [ ] gRPC unary + server-streaming + bidi work through the tunnel with
      interception **on** (the ADR 0077 default).
- [ ] `grpc-status` propagates (trailers preserved).
- [ ] HTTP/1.1 clients: zero behaviour change; the existing `internal/mitm` suite
      passes unmodified apart from C2's move.
- [ ] An h2 SSE stream's first byte arrives with unchanged latency (D1's
      invariant, on the new path).
- [ ] A streaming h2 request with no Content-Length forwards and does **not**
      deadlock — the ticket's stated blocker, as an assertion.
- [ ] The body-policy coverage rule (§4) is stated in the ADR + README, and
      surfaced at runtime once per session when it bites.
- [ ] `:authority` mismatch is rejected and audited.
- [ ] AGE-222's downgrade notice is gone; GOTCHAS §12 updated.
- [ ] ADR written, numbered from `main`, `make adr-check` green,
      `make licenses` run.
